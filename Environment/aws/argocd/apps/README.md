# AWS Argo CD app-of-apps (per environment)

`dev/` and `prod/` are what each environment's `envs/*/02-platform` root Application points at — the AWS equivalent of `Environment/local/argocd/apps/`.

## What's here now

- **Strimzi operator** (`kafka/`) — same chart/pattern as local, pointed at an AWS-specific values file (`../../values/strimzi-values-{dev,prod}.yaml`) since each AWS cluster only ever hosts one environment, unlike local's single cluster watching two namespaces.
- **Splitwise Kafka runtime** (`splitwise/runtime/`) — Kafka cluster, producer/loadgen Rollouts, Kafka UI, all via the **same shared base** local uses (`Environment/resources/splitwise-runtime/base/`, extracted from what used to be `Environment/local/argocd/apps/splitwise/runtime/base/`). Only the ingress differs per environment on purpose: local keeps its own Traefik + `localtest.me` ingress (no DNS locally), AWS gets its own ALB + `external-dns` ingress here (`splitwise/runtime/kafka-ui-ingress.yaml`) — the base itself has zero ingress-controller-specific content, so nothing had to change to support both.
- **The Splitwise app itself** (`splitwise/app/`) — the web/consumer container from `splitwise-household-expenses`, deployed **without any change to that repo**. `deployment.yaml`/`service.yaml`/`pvc.yaml`/`service-monitor.yaml` are pulled straight from its `k8s/base` by raw GitHub URL (not a local cross-repo path — Kustomize's security sandbox blocks that; a remote URL isn't subject to it), which also means that directory's own `kustomization.yaml` — and the KSOPS generator it lists for its encrypted `configmap.yaml` — is never invoked, so no KSOPS install is needed on AWS. Config and credentials both come exclusively from Secrets Manager instead: a placeholder empty `ConfigMap` satisfies the Deployment's `envFrom` reference (Kubernetes just needs the object to exist), and the real values — all 13 keys, config and credentials merged — arrive via `ExternalSecret` from `splitwise/<env>/app-config`, the same secret `terraform-aws-envs.yaml` populates by decrypting the app repo's SOPS-encrypted files directly (see the root README's Secrets section). This is deliberately the industry-standard path for a production AWS setup — Secrets Manager, not SOPS-in-git — chosen specifically to keep the app repo untouched while still avoiding a second, parallel secrets mechanism. Since the Deployment itself can't be edited (it's pulled by URL), a `patches:` entry here adds pod-level `securityContext.fsGroup: 10001` — a freshly provisioned `gp3`/EBS volume is root-owned by default, and without a matching `fsGroup` the containers' existing `runAsUser: 10001` can't write to it at all (`sqlite3.OperationalError: unable to open database file`, hit live; local's k3d storage doesn't have this restriction, so it never surfaced there).
- **Argo Rollouts** (`argo-rollouts/`) — controller + dashboard, same chart as local, at sync-wave `-1` so its CRDs exist before `splitwise/runtime`'s producer/loadgen `Rollout` resources try to sync. Without this, `splitwise/runtime`'s entire Application fails to sync at all (a kustomize failure on one resource blocks the whole Application, not just that resource) — which also silently prevented Kafka itself from ever being created, since it's bundled in the same Application. Confirmed live on dev.
- **The monitoring stack** (`monitoring/`) — Prometheus Operator, Prometheus, Alertmanager, Grafana, Loki, same 5-Application split and sync-wave ordering as local (`prometheus-operator` at wave `-1` so its CRDs land before anything that needs them, `loki` at wave `1` since it has no CRD dependency at all). `prometheus-extra`/`grafana-extra` (ServiceMonitors, PrometheusRules, the Kafka dashboard) are **shared with local** at `Environment/resources/monitoring/`, same reasoning as the runtime base. Two real differences from local, both deliberate: ingress is ALB + `external-dns` + HTTPS via cert auto-discovery (no hardcoded `certificate-arn` — the ACM cert's ARN isn't stable across a `dns` re-apply, `create_before_destroy` — the ALB controller finds a matching cert by hostname instead, using IAM permissions it already has), and Prometheus + Loki get real persistent storage (`gp3`, the EBS CSI driver — the cluster's built-in `gp2` StorageClass uses the deprecated in-tree provisioner and doesn't actually work, confirmed live) since losing metrics/log history on every pod restart isn't acceptable for a real environment the way it was for a disposable k3d cluster.

Every tree here is `kustomize build`-verified against the real files — including a full regression build of local's entire `apps/` tree after each extraction (confirming local wasn't affected), and of `splitwise/app/` against the actual live app repo content.

## What's still missing

- **prod's equivalent of `splitwise/app/`, `monitoring/`, and `argo-rollouts/`** — dev's are built and verified; prod needs the same files with `splitwise/prod/app-config` and the prod hostname/namespace, not yet created.
- **A single `ApplicationSet` generating dev/prod from one definition**, the way local's Splitwise apps do — dev and prod are currently two hand-maintained, parallel trees instead.
- **Real Alertmanager receivers** — `config.receivers` is still just `'null'` (alerts fire but go nowhere), same as local. Fine for now; wire up Slack/email/PagerDuty when there's someone to actually page.
